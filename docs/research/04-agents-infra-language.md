## 1. Executive summary

### 1.1 The language recommendation

**Write the core in Python now. Use TypeScript for the web UI. Move to Rust later, as optional native extensions, only where profiling shows a real hot spot. Do not do a Rust-first rewrite.**

| Layer | Language now | Language later | Why |
|---|---|---|---|
| (a) Orchestrator, agents, protocol, LLM layer, CLI, MCP server | **Python 3.12/3.13** (Apache-2.0) | Python, with optional Rust wheels via PyO3/maturin | Python has the best and fastest-moving LLM ecosystem: every agent SDK ships Python first, and the Anthropic SDK, MCP SDK, Pydantic AI and LangGraph are all Python. Validation already runs in Rust, because `pydantic-core` is Rust. LLM latency (seconds) dwarfs orchestration overhead (milliseconds). |
| (b) Blender adapter | **Python (bpy)**, GPL-3.0-or-later | Python, forever | Blender's only scripting API is Python, and the `bpy` 5.3 wheel requires exactly Python 3.13. There is nothing to choose here. Hot loops inside Blender use `foreach_get/foreach_set` + numpy or Geometry Nodes, not a new language. |
| (c) Godot adapter | **GDScript** editor/runtime plugin (MIT) + a thin **Python** client in core | Optionally a Rust GDExtension (gdext, MPL-2.0) for heavy runtime tooling | Every LLM writes GDScript well, it needs no build step, and it works in `--headless`. GDExtension adds native builds per platform, and its WASM support is experimental. |
| (d) Future native AI-first viewport/renderer | **Not now.** Phase 1 uses **TypeScript + three.js (WebGPU/WebGL2)** for a viewer | **Rust + wgpu** shared crate (`animatica-scene`), compiled both to a PyO3 wheel and to WASM | wgpu (MIT/Apache) runs natively and in the browser. A Rust scene core can serve the Python core (PyO3) and the web viewer (wasm-bindgen) from one codebase. Bevy is too unstable as a foundation today (4 breaking releases in ~13 months), but it is good for experiments. |
| (e) Web UI / production log viewer | Phase 0: **static HTML generated by Python** (Jinja). Phase 1+: **TypeScript** (Vite + Svelte/React + three.js) | TypeScript, possibly embedding the Rust/WASM viewport | The contributor pool and the 3D-on-web ecosystem are in TS. three.js is MIT, very active (r187, 2026-10-30), and ships WebGPURenderer and TSL. |

**Mixed, but for a reason.** Python is the "brain" and the glue. GDScript and bpy-Python are dictated by the engines. TypeScript is the face. Rust is a later "muscle" layer for deterministic, CPU-heavy, reusable code: scene diffing, USD I/O, frustum and intersection checks, mesh metrics, and the viewport. The batched JSON protocol (JSON Schema generated from Pydantic) is the language-neutral contract that makes this possible. **Keep the protocol schema as the single source of truth, and generate the TS types (and later the Rust serde types) from it.**

**Why not Rust-first?** (1) There is no first-class Rust agent SDK from Anthropic or OpenAI to match the Python and TS ones. (2) Blender cannot be driven from Rust in-process. (3) The real bottlenecks are LLM round-trips and Blender renders, and neither gets faster in Rust. (4) The art/TD contributor pool writes Python. (5) PyO3 0.30 + maturin 1.16 make adding Rust later a low-cost, incremental change that doesn't break anything.

**Why not TypeScript-first?** TS is a credible orchestrator language: the MCP TS SDK, the OpenAI Agents JS SDK, LangGraph.js, Mastra and the Vercel AI SDK are all good. But it puts a language boundary between the core and *both* engine adapters' tooling. It also loses numpy/trimesh/usd-core/open_clip/transformers for critic pre-filters and geometry checks. And the official Claude Agent SDK for TypeScript is **not open source** (Anthropic Commercial Terms), while the Python one is MIT.

### 1.2 Other headline recommendations

1. **Orchestrator: build a thin custom one in Python** (asyncio task graph + JSONL production log + budget guard). Use **Pydantic AI** (MIT) as the optional model/tool/structured-output layer. Its `TestModel`/`FunctionModel` map directly onto the PLAN's "scripted offline provider". **TRIAL LangGraph** (MIT) only if checkpoint/resume needs outgrow the custom graph. **AVOID AutoGen**: Microsoft has archived it and points users to Microsoft Agent Framework.
2. **Treat the Claude Agent SDK as one optional "agent runtime" backend, not the foundation.** It is MIT, but it bundles the Claude Code CLI under Anthropic's Commercial Terms, and it is Claude-only. It is excellent for the Gameplay-Programmer agent, which edits files, runs Godot and reads logs.
3. **MCP: expose our own server with the official Python SDK `mcp` (MIT, v2.3.0) or FastMCP (Apache-2.0, v4.2.0).** Target spec **2026-07-28**, and use the **Tasks** extension for long renders. Build our own Blender add-on and borrow the *socket-bridge pattern* from `ahujasid/blender-mcp` (MIT, ~33k★). Study, but do not copy, the **official Blender Lab MCP** (GPL-3.0-or-later, v1.0.0, April 2026, used by Anthropic's Blender connector). Its code is GPL-compatible with our GPL add-on, but not with the Apache core.
4. **Godot: our own GDScript plugin, plus headless runs.** Note that `--headless` **cannot render**, so screenshots and playtest frames need a real rendering driver under Xvfb, or Movie Maker mode. Use `Coding-Solo/godot-mcp` (MIT, TS) as reference, GUT/gdUnit4 (MIT) for tests, and `godot-ci` (MIT) for web export.
5. **Vision critique: put the cheap checks first.** The order is geometry checks → image statistics → CLIP/aesthetic pre-filter → small VLM → large VLM, only on disagreement. A 480×270 preview costs ~180 image tokens on Claude, and Haiku 5.5 input is $0.10/MTok, so a full-quality critic per batch costs a fraction of a cent. For local critics, use **Qwen3-VL (Apache-2.0, 2B–235B)** or **Qwen3.5** small multimodal models. **Avoid aesthetic-predictor-v2.5 (AGPL-3.0)**.
6. **Infrastructure: no job queue in v0.** Use subprocesses + a local work directory. Add **RQ (BSD-2)** or **Celery (BSD-3)** when we parallelize renders. Use **Temporal (MIT)** or **Prefect (Apache-2.0)** only for hosted, multi-hour, multi-user runs. **Flamenco (GPL-3.0)** is a good optional render farm because it runs as a separate service. **Avoid MinIO** (AGPL, upstream repo unmaintained) and Garage (AGPL). Use local disk/S3, with **SeaweedFS (Apache-2.0)** if self-hosting is needed.

## 2. Language decision — detailed analysis

### 2.1 Hard constraints discovered

| Constraint | Evidence | Consequence |
|---|---|---|
| Blender scripting is Python-only. The `bpy` PyPI wheel 5.3.0 (2026-11-10) requires `==3.13.*` and is GPL-3.0. | PyPI `bpy` page | The Blender adapter is Python. Pin the adapter venv to 3.13. The **core must not `import bpy` in-process** (see License traps §8), so it talks to Blender via subprocess or socket. |
| Blender Extensions platform only accepts GPL-compliant software | extensions.blender.org/about | The add-on is GPL-3.0-or-later, as the PLAN already says. |
| `usd-core` 26.11 (2026-10-21) wheel exists for Python 3.11–3.14, under the "Tomorrow Open Source Technology License 1.0" (Apache-2.0 with a different trademark clause) | PyPI, OpenUSD LICENSE.txt | USD I/O is easy from Python. Rust has only young crates (`openusd` 0.8.0, MIT, pure-Rust reader). |
| Godot 4 `--headless` uses a dummy renderer and can't render | Godot Q&A | Visual playtests need Xvfb + an OpenGL/Vulkan driver (llvmpipe/lavapipe on CPU). This is a choice of infrastructure, not of language. |
| gdext (Rust for Godot) is MPL-2.0 and "usable" with occasional breaking changes; WASM is experimental | gdext README | Don't put Rust on the Godot critical path yet. |
| Claude Agent SDK: Python = MIT; TypeScript = proprietary (Commercial Terms); the Python wheel bundles the Claude Code CLI | raw LICENSE files, SDK README | A Python core keeps the open-source story cleaner. |
| PyO3 0.30.1 (2026-10-14), maturin 1.16.0 (2026-10-29), both MIT/Apache | crates.io, PyPI | Adding Rust later is low-risk. |
| wgpu 30.0.2 (2026-11-12) MIT/Apache; Bevy 0.20 (2026-10-08) MIT/Apache, after 0.17 (2025-09), 0.18 (2026-01) and 0.19 (2026-06) | crates.io, bevy.org/news | wgpu is a stable foundation. Bevy's API churn is a maintenance tax. |

### 2.2 Where performance actually matters (and what fixes it)

| Hot spot | Size in our pipeline | Right fix |
|---|---|---|
| Validating a 300-op batch | Microseconds to milliseconds with Pydantic v2, whose core is Rust | Nothing. Already fast. |
| Semantic checks (ids exist, keyframes ordered, frustum and bounding-box checks) | ms, with numpy | Python + numpy. Move to Rust (PyO3) only if scenes reach 10⁵–10⁶ objects. |
| Geometry processing (mesh cleanup, metrics, intersection) | Inside Blender: bmesh + `foreach_get` + numpy. Outside: trimesh (MIT, 5.2.1, 2026-11-12) | Python. Rust later for a shared validator that also runs in the web viewer. |
| Preview rendering | Seconds (Workbench/EEVEE) | Blender's C++ engine, plus resolution and sample settings. Language doesn't matter. |
| LLM calls | Seconds to minutes, and dollars | Batching, caching and small models (§4.3). Language doesn't matter. |
| Web viewport of large scenes | Browser-bound | three.js now. Rust/wgpu→WASM later if needed. |

**Conclusion:** no current hot spot justifies Rust. The *strategic* reason for Rust is the long-term vision in PLAN §9: a native, AI-first scene core and viewport that can replace Blender subsystems and run in the browser and on the desktop. Prepare for it by keeping the scene model USD-shaped and engine-neutral, not by writing Rust in month one.

### 2.3 Phased language strategy

| Phase | Python | TypeScript | Rust | GDScript |
|---|---|---|---|---|
| **Now (0–4 weeks)** | Everything core. Blender add-on/runner. Static HTML log. | — | — | Godot plugin + runner scripts |
| **3 months** | Core stable. Protocol JSON Schema exported. `animatica-protocol` types published. | Log viewer/Studio UI (Vite + Svelte or React), three.js preview of the scene model / glTF exports, generated TS types | Spike: `animatica-scene` crate (serde model mirroring the protocol, diff/merge, frustum/bbox checks), with a PyO3 wheel *optional* and pure-Python fallback kept | Playtest harness (input replay, GUT tests) |
| **1 year** | Orchestrator plus plugins | Studio UI embeds the WASM viewport | `animatica-scene` is the canonical diff/validate engine (Python and WASM). A wgpu viewport prototype (WebGPU in the browser, native in the desktop app). USD I/O via `openusd` crate or usd-core bridge | Optional gdext extension if runtime perf requires it |

**Rules that keep this from turning into a rewrite.** (1) Every Rust component has a Python fallback or is behind a feature flag until it has proved itself. (2) The protocol schema is generated from Pydantic, and all other languages consume it. (3) CI builds abi3 wheels with maturin for the Rust parts, so `pip install animatica` never needs a Rust toolchain.

### 3.2 Why a thin custom orchestrator wins here

- The PLAN's distinctive requirements are a **batched op protocol**, **validate→execute→verify**, **hard budgets**, a **fully offline scripted provider**, and an **artist-readable production log**. All of them are orchestration *policy*, and every framework would have to be bent to fit. The core loop (plan → batch → preview → critique → fix, at most N times) is about 300–600 lines of Python.
- Long-running needs (resume a 2-hour render job) are better met with **idempotent tasks, content-addressed artifacts, and a persisted task-graph state file** than with a framework runtime. Add Temporal or Prefect only when the system is multi-user or hosted.
- Avoid the "agents chatting" pattern (AutoGen/AG2/CrewAI group chat). It multiplies tokens. FilmAgent's data shows the useful forms of multi-agent collaboration are **structured** ones, such as Critique-Correct-Verify and Debate-Judge (§7).

## 5. Godot automation (and Bevy)

### 5.1 Facts that drive the design

- **Headless:** Godot 4's `--headless` sets dummy display and audio drivers and **cannot render** (this differs from Godot 3's `--no-window`). Use it for `--import`, `--check-only`/script validation, `--export-release` and logic-only playtests. For screenshots or video, run under **Xvfb** with `--rendering-driver opengl3` (Compatibility), or Vulkan via Mesa lavapipe on CPU runners. **Movie Maker mode** (`--write-movie`, fixed-fps offline capture) is the deterministic way to record playtest footage.
- **Current version:** stable docs and releases track **Godot 4.7**. 4.7 adds per-platform export-template downloads, which helps CI, and `Tween.tween_await()`.
- **Testing:** **GUT** (MIT; 9.7.1 targets 4.7) and **gdUnit4** (MIT) both have CLI runners. Use them for generated-game regression tests.
- **CI export:** **godot-ci** (MIT; Docker image + GitHub/GitLab workflows, deploys to Pages and itch.io). Web export needs export templates. Threaded web builds need cross-origin isolation headers, while single-threaded web export avoids that on static hosts like GitHub Pages.
- **GDScript generation:** LLMs write GDScript well. Validate generated scripts with `godot --headless --check-only -s file.gd`, or load the project with `--quit-after N` and parse stderr. Feed only the errors back, tersely.

### 5.2 Recommended Godot adapter

1. `adapters/godot/addons/animatica/` holds an MIT **GDScript EditorPlugin + runtime autoload** that executes the batched ops (scene-tree ops, write/attach scripts, input map, resources). Live mode uses a localhost TCP/WebSocket; batch mode uses `godot --headless -s runner.gd -- batch.json`.
2. A **Playtester** autoload replays scripted input timelines at a fixed physics tick, asserts win/lose signals, and dumps compact JSON (errors, reached states, FPS). A visual variant runs under Xvfb and takes 4–9 screenshots per run, tiled into one contact sheet for the Critic.
3. CI builds web and Linux exports with the godot-ci image.

## 6. Vision critique

### 6.1 Critic pipeline (cheapest first)

1. **Geometric/semantic checks** inside Blender or Godot, with no image: subject bounding box inside the camera frustum, floor penetration (min-z vs floor), lights present, camera not inside a mesh, motion present (keyframe deltas), visemes present while dialogue plays. This catches most "broken" outputs deterministically.
2. **Image statistics:** mean and percentile luminance (black or blown-out frames), the fraction of background pixels where the subject should be (via an object-ID/cryptomatte pass), frame-to-frame difference (static shots, jitter).
3. **Learned pre-filters:** CLIP score (prompt alignment) via **open_clip** (MIT, 4.2.2, 2026-11-10) or torchmetrics (Apache-2.0); **LAION aesthetic predictor** (MIT / improved-aesthetic-predictor Apache-2.0); PickScore (MIT) and ImageReward (Apache-2.0). Use them **only as relative signals** (A vs B, or this iteration vs the last), never as absolute pass/fail. Check the *weights'* licenses separately from the code's.
4. **Small VLM critic** (Claude Haiku-class via API, or local Qwen3-VL-8B / Qwen3.5-9B) with a rubric and **structured output** (pass/fail plus a fix list with object ids). Send the contact sheet plus a compact scene summary.
5. **Large VLM only for disagreements**, for final-shot approval, or for Director-level "does this tell the story" checks.

### 6.3 What research says about VLM critics

- **BlenderGym (CVPR 2025):** even the strongest VLM systems struggle with edits that experienced Blender users find easy. The *verifier* also benefits from inference scaling, and splitting compute between generation and verification helps. So budget critic calls explicitly, and use several candidates plus a verifier rather than one long chain.
- **SceneCraft (ICML 2024):** a scene graph is planned first, then turned into Blender code with numerical constraints, then a VLM critiques the render, and reusable functions are collected into a library. This validates our plan → batch → preview → critique loop and suggests a **learned recipe library** in `knowledge/`.
- **BlenderAlchemy (ECCV 2024):** pairs an edit generator with a VLM state evaluator searching over edits, and uses generated reference images to "imagine" targets. That suggests the Critic compare against a style-bible reference image, not text alone.
- **FilmAgent:** feedback was text-only and its authors list the missing multimodal verification as a limitation. That is exactly the gap our Critic fills.

## 10. License traps

1. **Never `import bpy` in the Apache core.** `bpy` is GPL-3.0. Loading it in-process with the core arguably makes a combined GPL work. Keep Blender in a separate process (subprocess or socket), as PLAN §7 intends. Put the adapter's `bpy`-based tests under `adapters/blender/`.
2. **Blender Lab's official MCP is GPL-3.0-or-later.** Its code may go only into our GPL add-on, never into `src/animatica`.
3. **The Claude Agent SDK TypeScript package is proprietary.** The Python SDK is MIT but **bundles the Claude Code CLI under Anthropic's Commercial Terms**. Make it an *optional extra* (`animatica[claude-agent]`), never a hard dependency or a vendored binary.
4. **AGPL:** OpenMontage (ideas only), aesthetic-predictor-v2.5, MinIO, Garage. Don't copy, bundle or ship them.
5. **No licence = all rights reserved:** CommonSenseMachines/blender-mcp and showlab/MovieAgent (no LICENSE file found). LL3M uses an evaluation-only "Demonstration License".
6. **MPL-2.0 (gdext)** is file-level copyleft: modified gdext files must stay MPL. Fine as a dependency.
7. **Model weights ≠ code licence.** Qwen3-VL is Apache-2.0. Many others (Gemma, Llama, some InternVL sizes, some aesthetic or reward heads trained on restricted data) are not OSI. Record each *weights* licence in `THIRD_PARTY.md`.
8. **Piper TTS moved to `OHF-Voice/piper1-gpl` (GPL-3.0).** The old `rhasspy/piper` was MIT. Run it as a subprocess, or pin the old MIT release, and check the licence of each voice model. This overlaps with the audio research topic.
9. **Telemetry defaults:** CrewAI (anonymous telemetry on by default) and blender-mcp (anonymous usage telemetry on by default). Disable them in any integration and document it.
10. **MCP TS SDK** contributions are moving from MIT to Apache-2.0. Both are compatible with Apache-2.0, so just keep notices.
11. **OpenUSD/usd-core** uses the TOST-1.0 licence (Apache-2.0 with a modified trademark section). It is compatible, but don't use "USD/Pixar" marks in branding.
12. **GitHub larger and GPU runners are billed even for public repos.** That is not a licence issue, but it is a cost trap for an open-source project's CI.
